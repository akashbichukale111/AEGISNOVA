# Warrant & warranty
Warrant fields: warrant_id, repo_id, base_sha, patch_hash, path_scope (fnmatch globs), allowed_actions (`static`,`test_execution`), expires_at, policy_version, issuer, nonce, status, mac, test_only. MAC = HMAC-SHA256(canonical JSON without mac) with `IRA_WARRANT_KEY`; only `test_only` warrants verify with the built-in TEST key. Results: NO_WARRANT, MALFORMED, BAD_MAC, REVOKED (status or `.data/revoked.json`), EXPIRED, OVER_BROAD, MISMATCH, VALID. Re-checked before the after-patch run and finally. Authority ≠ correctness. No upstream approval service is simulated.
Warranty states: ACTIVE, AGING (>half window since revalidation), EXPIRED, INVALIDATED (patch hash or covered file changed; sticky), REQUIRES_REVALIDATION (triggers: base_branch_change, dependency_advisory, test_change, policy_update, failed_recheck), SOURCE_UNAVAILABLE, SUSPENDED (manual state; no command sets it yet). Evaluate against the repo **with the repair applied** (a snapshot is stored). Manual revalidation: `ira warranty revalidate <id> --repo-dir DIR` / `POST /v1/warranty/{id}/revalidate`; that function is the scheduler hook (no scheduler included). The original proof is never overwritten. Time-bounded commitment, not a guarantee.
